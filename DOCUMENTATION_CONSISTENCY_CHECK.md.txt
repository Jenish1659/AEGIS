**Document Type:** Documentation Audit and Validation Guide  
**Project:** AEGIS – Task-Aware Runtime Security Gateway for Autonomous AI Agents  
**Purpose:** Verify that all project documentation is complete, technically consistent, secure, and ready for implementation.  
**Review Status:** Pending  
**Implementation Status:** Not started

---

# 1. Purpose

This document defines the complete process for reviewing all AEGIS project documentation before starting source code development.

The purpose is not simply to check whether all Markdown files exist.

The review must verify that:

- Every document follows the same project concept.
- Technical decisions are consistent across files.
- Security rules do not conflict.
- Architecture and implementation instructions match.
- API definitions match backend requirements.
- Database structures match application workflows.
- OPA policies match the Task Contract design.
- Gemini has clearly defined limitations.
- Frontend features match available backend functionality.
- Testing requirements cover the main security risks.
- Development phases follow the correct implementation order.

The reviewer must inspect the actual contents of every document.

**Important:** Never mark a check as PASS simply because a document mentions the required topic. The actual content must be reviewed.

# 3. Review Rules

The documentation reviewer must follow these rules.

1. Read all 15 files before making final conclusions.
2. Do not assume that two similar statements mean the same thing.
3. Compare related sections across multiple files.
4. Identify contradictions, missing details and unclear instructions.
5. Verify technical claims against the selected technology and its actual capabilities.
6. Do not invent features that have not been approved.
7. Do not remove important requirements just to make documents shorter.
8. Do not change the project concept without approval.
9. Do not claim that a feature is implemented when it is only planned.
10. Preserve the distinction between MVP features and future improvements.
11. Never weaken a security rule to resolve a documentation conflict.
12. Record all identified problems before modifying documents.
13. Apply corrections consistently across every affected file.
14. Recheck corrected documents after making changes.
15. Do not start application development during this documentation review.

# 5. Critical Architecture Consistency

This section is mandatory.

The architecture must describe one clear and consistent request flow.

## 5.1 Approved Request Flow

The expected flow is:

```text
AI Agent
   |
   v
Agent Authentication
   |
   v
Request Validation
   |
   v
Active Task Contract Validation
   |
   v
Deterministic Security Checks
   |
   +---- Mandatory violation? ---- YES ----> BLOCK
   |
   NO
   |
   v
Is Additional Context Required?
   |
   +---- NO -----------------------------+
   |                                     |
   +---- YES --> Gemini Advisory Analysis
                                         |
                                         v
                                  Trusted Backend Input
                                         |
                                         v
                                   Final OPA Decision
                                         |
                   +---------------------+------------------+
                   |                     |                  |
                   v                     v                  v
                 ALLOW                 BLOCK              REVIEW
                   |                     |                  |
                   v                     v                  v
             Tool Execution          Reject Request     Human Review
                   |                                        |
                   v                                        v
              Audit Record                              Revalidation
```

The implementation may refine the flow, but every document must describe the same approved sequence.

## 5.2 Important Architecture Rules

- Agent authentication must happen before trusting agent identity.
- Agent identity must come from validated authentication, not an untrusted request-body field.
- Task Contracts must be stored and validated by the backend.
- Agents must not create or modify their own trusted permissions.
- Deterministic mandatory restrictions must not depend on Gemini.
- Gemini should only be called when additional context is genuinely required.
- Gemini output must be validated before use.
- OPA must make the final policy decision.
- The backend gateway must enforce the decision.
- A BLOCK decision must prevent tool execution.
- A REVIEW decision must prevent execution until approval and revalidation.
- An ALLOW decision permits execution only through the protected gateway.

## 5.3 Architecture Conflict to Check

Do not allow one document to describe:

- OPA making the final decision before Gemini analysis.

While another document describes:

- Gemini analysis happening before the final OPA decision.

The approved design is:

**Authentication → Task Contract → Deterministic Checks → Optional Gemini Analysis → Final OPA Decision → Gateway Enforcement.**

A deterministic hard violation can be blocked before Gemini or OPA because it must never be overridden.

If a different architecture is intentionally selected, update this document and every related document together.

# 8. OPA Policy Consistency

Review:

- `ARCHITECTURE.md`
- `BACKEND.md`
- `AGENT_RULES.md`
- `OPA_POLICY_DESIGN.md`
- `SECURITY_MODEL.md`
- `TESTING_STRATEGY.md`

Verify that all documents agree on the following:

1. OPA is the Policy Decision Point (PDP).
2. AEGIS gateway is the Policy Enforcement Point (PEP).
3. The backend creates trusted policy input.
4. Agents cannot send policy input directly to OPA.
5. The default decision is BLOCK.
6. Mandatory restrictions cannot be overridden.
7. Review conditions produce REVIEW.
8. Only valid authorization produces ALLOW.
9. Missing or invalid OPA results prevent execution.
10. The gateway enforces the final decision.

## 8.1 Decision Priority

Use the following priority:

```text
BLOCK > REVIEW > ALLOW
```

Meaning:

- If a mandatory restriction is violated, BLOCK.
- If the request needs approval or cannot be safely resolved, REVIEW.
- ALLOW only when all required checks pass.

No document should suggest that a Gemini recommendation can override a mandatory BLOCK condition.

## 8.2 OPA Input and Output

The policy input structure must match the backend's trusted data model.

Verify consistency for:

- Agent identity.
- Task Contract.
- Contract version.
- Tool name.
- Operation.
- Resource.
- Deterministic security results.
- Validated context signals.
- Approval state, where applicable.

The policy output should use one documented response structure containing at least:

- Decision.
- Reason code.
- Human-readable reason.

The backend must validate the response before enforcing it.

## 8.3 Policy Testing

The policy documentation and testing strategy must agree on:

- Rego version and syntax.
- Policy package and rule names.
- Test directory.
- Expected decision cases.
- Default-deny behavior.
- BLOCK priority.
- REVIEW behavior.
- Invalid input handling.

The documented OPA test command must be verified against the actual installed OPA version.

## 11.2 Important Distinction

An authorization decision and a tool execution result are not the same thing.

Example:

```text
Authorization Decision: ALLOW
Execution Outcome: FAILED
```

The request was permitted, but the protected tool failed.

The database must not treat this as a successful execution.

Similarly:

```text
Authorization Decision: BLOCK
Execution Outcome: NOT_EXECUTED
```

The blocked action must not be recorded as executed.

## 11.3 Audit Integrity

Do not claim that ordinary SQLite or PostgreSQL audit tables are cryptographically tamper-proof.

If stronger tamper detection is required in the future, define and implement a separate integrity mechanism.
